# Database Choices

## 1. ทำไมโปรเจกต์นี้เลือก SQLite แทน MongoDB
เนื่องจากข้อมูลของระบบ Campus Service มีโครงสร้าง (Schema) ที่ชัดเจนและมีความสัมพันธ์กันระหว่างตาราง ตัวอย่างเช่น ตารางคำร้อง (`requests`) มีการอ้างอิงถึงตัวผู้ใช้งาน (`users`) การใช้ SQLite ซึ่งเป็นฐานข้อมูลเชิงสัมพันธ์ (Relational Database) จะทำให้เราสามารถใช้คำสั่ง SQL (เช่น `JOIN`) ในการจัดการข้อมูลที่มีความสัมพันธ์กันได้ง่ายและตรงจุดกว่า MongoDB ซึ่งเป็น NoSQL ที่เหมาะกับข้อมูลแบบ Document

## 2. ถ้าวันหนึ่งต้องเปลี่ยนไป MongoDB จะกระทบชั้นไหนบ้าง
จะกระทบตั้งแต่ชั้น **Database/Service Layer** ไปจนถึงชั้น **Controller Layer** เลย
ที่ต่างจากการแก้ครั้งก่อนๆ เพราะไลบรารีของ SQLite บางตัว (เช่น `better-sqlite3`) สามารถทำงานแบบ Synchronous ได้ (สั่งปุ๊บได้ข้อมูลปั๊บ) แต่ถ้าเปลี่ยนไปใช้ MongoDB การดึงข้อมูลทั้งหมดจะต้องเปลี่ยนเป็นแบบ Asynchronous ทำให้เราต้องไปตามใส่ `async` / `await` ในทุกๆ ฟังก์ชันที่เรียกใช้ฐานข้อมูลและใน Controller ที่เรียกใช้ Service เหล่านั้นด้วย

## 3. async จำเป็นเมื่อไร ไม่จำเป็นเมื่อไร
- **จำเป็นต้องใช้ async:** เมื่อฐานข้อมูลอยู่คนละเครื่องกับเซิร์ฟเวอร์ API (หรือรันอยู่คนละ Process เช่น MongoDB, MySQL, PostgreSQL) เพราะการดึงข้อมูลต้องวิ่งผ่านเครือข่าย (Network) ซึ่งมีความหน่วงเวลา (Latency) ระบบจึงต้องทำงานแบบรอ (Asynchronous) เพื่อไม่ให้การทำงานส่วนอื่นค้าง
- **ไม่จำเป็นต้องใช้ async:** เมื่อฐานข้อมูลเป็นเพียงไฟล์ในเครื่องเดียวกัน (Local File) อย่าง SQLite การอ่านเขียนไฟล์จากดิสก์โดยตรงนั้นทำงานได้รวดเร็วมากจนสามารถเขียนโค้ดแบบทำงานตามลำดับ (Synchronous) ได้
